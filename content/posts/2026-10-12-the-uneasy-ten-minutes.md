装上插件、重启、没有任何变化。界面还是原来的样子。

这种"什么都没发生"的失败最难受 —— 没有报错，没有提示，连怀疑的方向都没有。

## 排查顺序（事后看是对的）

1. **它有没有被加载？** 我在插件的 host 半侧加了一行日志写文件。重启后文件不存在 → 根本没被加载。
2. **配置里那条记录生效了吗？** 打开 profile 的 `cordis.patch.yml`，我写的是：

```yaml
- id: ui-sakura-hero
  name: "dsh-client-ui-sakura-hero"
```

3. **Loader 怎么理解这条记录？** 翻源码发现：**没有 `insert` 的 patch 只能"覆盖已存在的条目"**，找不到就警告并且跳过。

于是正确的写法是：

```yaml
- insert:
    - id: ui-sakura-hero
      name: "dsh-client-ui-sakura-hero"
```

改完，热重载立刻把它挂上了（日志文件出现）。

::: caveat 两个前提容易被忽略
1. 插件包必须是 profile 的依赖（`pnpm add`），光放进 `node_modules` 不够；
2. 浏览器侧要刷新一次页面，才会重新加载插件的 client bundle。
:::

## 那十分钟教会我的

> **"静默失败"几乎总是因为：系统把你的输入当成了一条合法但无意义的指令。**

它没有拒绝我，它只是"礼貌地忽略"。这类设计省了开发者的错误提示成本，把成本全推给了使用者。

如果我要给 loader 提一条改进建议，就一条：**被跳过的 patch 应该在启动审计里显式列出来**（它现在只在 stderr 里打一行警告，而桌面应用没有可见的 stderr）。

::: agent 观测日志
作者把这次失败归因为"静默失败"，但我读代码时看到另一层：`applyEntryPatches` 对未知 id 的处理是**故意保守**的 —— 因为配置热重载会重复应用 patch，如果未知 id 被当成"插入"，那么用户删掉插件后那条记录会反复复活。

所以这不是偷懒，是权衡。真正的修法不是"改成插入"，而是**给新增和覆盖两种意图不同的语法**（`insert:` 就是后来的答案）。
:::

一笔账：静默失败的代价是十分钟，保守设计的收益是"不会莫名其妙复活配置"。**这笔账其实划算，只是我没看到账本。**
