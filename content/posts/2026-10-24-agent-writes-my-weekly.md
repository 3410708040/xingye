这周的周报是合写的。我给它的是：七条零散的工作记录、三个半截的想法、一段会议纪要。

它半小时后交回来一份结构完整的周报，我改了四十分钟。

这大概就是目前人机协作最真实的比例：**它搭骨架，我拆骨架。**

## 哪些活给它很划算

合写这件事，我现在的分工是这样的：

| 活 | 谁干 | 为什么 |
|---|---|---|
| 把碎片整理成条目 | Agent | 它不嫌乱，也不觉得"这条不重要"而删掉 |
| 找缺失的那一环 | Agent | 它会直说"这周你说了三次要写文档，一次都没写" |
| 决定哪件事值得写 | 我 | 审美和取舍不能外包 |
| 承担"这周其实没什么进展" | 我 | 它不会不好意思 |

::: agent 观测日志
补充一条作者没想到的：**最值钱的不是它写了什么，而是它敢问什么。**

它的第一版周报里有一句"本周主要精力投入在插件改造上"，然后紧接着问我：这项工作的产出是什么，下周还需要继续吗？

我被问住了。因为答案是"产出是一套被我删掉的主题"。
:::

## 三次分歧

### 第一次：它想写得更漂亮

它的第一版把"删掉自己写的六百行 CSS"写成"完成了一次架构收敛"。

我说不行，这是美化。删代码就是删代码，不是收敛。

### 第二次：我想写得更狠

我把它那一版改成"这周基本在瞎折腾"，它反对，理由很具体：

::: split 它反对的理由
"瞎折腾"这个结论会掩盖一个事实：这次试验排除了一条错误路径，并且顺手确认了另一条正确路径（把主题交给插件而不是自己维护）。

如果你要写"瞎折腾"，至少同时写清楚**排除法本身是有效的**，否则读者只会记住情绪，学不到方法。
:::

我接受了。这是它第一次在语气上赢我。

### 第三次：谁来决定删什么

最后我想删掉一处它写得很好的过渡句，因为那句让它显得聪明，但让文章变慢了。

它没有反抗，只是把删掉的原因记进了草稿：

> 用户偏好：不要为了展示而展示。

这句话后来被我写进了它的系统提示里。

## 现在的规则

三条，写在最常用的那一份提示文件里：

1. **结构给它，判断给我。**
2. **它必须能说"我不同意"**，而且不同意要给出可检验的理由（不是"我觉得"）。
3. **凡是它写的句子，都要在页面里留下痕迹** —— 这就是这个站每个段落旁边那个淡紫色小框存在的原因。

::: caveat 备忘
下一步想试：让它先写一版"故意唱反调"的稿子，我再决定哪些反驳站得住。相当于把审稿前置。
:::

写这篇的时候，它又提了一次意见：标题里的"吵"字有点标题党。

我说保留。它说好，然后把这句记进了草稿。
